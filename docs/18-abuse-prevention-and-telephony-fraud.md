# 18 — Abuse Prevention & Telephony Fraud

**This entire document addresses a risk category that wasn't in the original brief and is easy for a team without prior telephony experience to miss entirely**: a platform that can place or transfer phone calls is a target for a well-known, financially serious class of attack — toll fraud / International Revenue Share Fraud (IRSF) — that has nothing to do with the AI/CRM domain logic and everything to do with the fact that "this system can cause a phone call to happen" is itself a monetizable capability if compromised. A generic web-app security review (the kind [08-security-observability-reliability.md](08-security-observability-reliability.md) covers) will not catch this category by default — it needs its own explicit treatment.

## 1. Toll fraud / International Revenue Share Fraud (IRSF)

**The attack**: an attacker who obtains SIP trunk credentials, exploits an open/misconfigured trunk, or compromises an account with outbound-calling capability places (or triggers the platform into placing) a high volume of calls to expensive premium/international destinations that the attacker (or a colluding party) controls, profiting from termination fees while the platform's account absorbs the cost. This is one of the most common and expensive fraud categories against any business that owns SIP trunking, and it is entirely orthogonal to whether the application logic itself has bugs.

**Why this platform's specific design already reduces exposure, and where it doesn't**: this platform's _only_ outbound-calling capability is the emergency call-transfer feature ([07-notification-and-emergency.md](07-notification-and-emergency.md) §5.3, [02-voice-pipeline-and-telephony.md](02-voice-pipeline-and-telephony.md) §4) — transferring an active inbound call to a pre-configured on-call technician number. There is no general-purpose "place an outbound call to any number" capability anywhere in the tool registry ([04-ai-tool-architecture.md](04-ai-tool-architecture.md) §1) for the same reason there's no scheduling tool: **the capability that would need to be secured against misuse simply doesn't exist as a broad primitive.** This is the strongest possible mitigation — architectural absence — but the following controls remain necessary because the transfer capability itself is real and must be secured:

| Control                                                              | Implementation                                                                                                                                                                                                                                                                                                                                                                                                                                                                              |
| -------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Destination allowlist**                                            | Call transfer only ever dials numbers present in a business's own `oncall_shifts`/`business` configuration (see [06-database-schema.md](06-database-schema.md)) — never a number supplied by caller input, LLM output, or any other runtime-derived source. The transfer tool's implementation validates the target number against this allowlist immediately before dialing, rejecting anything else even if some other bug caused an unexpected value to reach that code path.            |
| **Geographic/destination-type restriction at the carrier**           | Twilio/Telnyx (the SIP carrier, [02](02-voice-pipeline-and-telephony.md) §4) account-level geographic permissions are configured to disable international and premium-rate destination classes entirely, since this platform has no legitimate reason to ever dial one — a carrier-level control that doesn't depend on the application layer behaving correctly.                                                                                                                           |
| **Per-tenant and platform-wide spend caps**                          | Hard caps on outbound-transfer-minutes per tenant per day (generous enough to never affect legitimate use, tight enough to bound worst-case exposure), enforced at the tool-broker rate-limiter layer already built for general abuse prevention ([04](04-ai-tool-architecture.md) §4) — the same mechanism, one more dimension.                                                                                                                                                            |
| **Destination-anomaly cost alerting**                                | Extends the cost-anomaly alerting already specified in [08-security-observability-reliability.md](08-security-observability-reliability.md) §2.3: an alert fires not just on total spend deviation but specifically on outbound-transfer calls to a destination number pattern never seen before for that tenant — a sudden transfer to an unfamiliar number is exactly the IRSF signature, and is a fraud signal distinct from (and faster to act on than) a pure dollar-amount threshold. |
| **SIP credential hygiene**                                           | Trunk credentials rotated on a schedule and immediately on any suspected compromise; IP allowlisting so the SIP trunk only accepts signaling from the platform's own known infrastructure IPs (§3), not the public internet at large.                                                                                                                                                                                                                                                       |
| **Vendor-native fraud detection enabled as a first line of defense** | Twilio/Telnyx and LiveKit both offer their own fraud-detection features (e.g. anomalous-calling-pattern detection, geographic permission controls) — enabling these is a near-zero-cost first layer that catches attack patterns the vendor sees across their entire customer base, which this platform alone cannot; the controls above are defense-in-depth on top, not a replacement for using what the vendor already offers.                                                           |

## 2. Traffic pumping / access stimulation (inbound-side variant)

A related but distinct scheme where a party controlling a rural or high-termination-fee inbound number artificially inflates _inbound_ call volume to that number to collect termination fees from the originating carrier. Lower relevance for this platform's threat model (its inbound numbers are legitimate business lines, not rented-out termination endpoints), but worth naming so it isn't confused with §1 by anyone reviewing the fraud surface — no dedicated control needed beyond the general inbound-volume anomaly detection in §4.

## 3. SIP trunk / signaling security

- **IP allowlisting**: the SIP trunk between the telephony carrier and the voice-orchestrator/LiveKit accepts signaling only from known carrier IP ranges — not open to the public internet.
- **TLS/SRTP**: SIP signaling over TLS, media over SRTP, not plaintext SIP/RTP — standard, non-negotiable for any production telephony deployment, called out explicitly here since it's easy to leave defaulted-off in a vendor's dashboard.
- **Credential rotation + failed-auth monitoring**: repeated failed SIP registration/auth attempts against the trunk are logged and alerted on (a `fail2ban`-equivalent pattern) — this is a distinct signal from application-layer rate limiting and belongs at the telephony/infrastructure observability layer ([08](08-security-observability-reliability.md) §2).

## 4. Inbound call abuse (spam/robocall callers, not fraud but a real cost/quality problem)

An AI receptionist that answers every call and runs STT/LLM/TTS for the duration is a **cost center per answered call** — unlike a human receptionist who can instantly recognize and dismiss a robocall, every inbound call (legitimate or not) consumes real STT/LLM/TTS spend ([09-cost-analysis.md](09-cost-analysis.md)) until the AI itself determines the call isn't worth continuing. This is a genuine, previously-unaddressed cost/abuse vector specific to this platform's nature:

- **STIR/SHAKEN attestation**: Twilio/Telnyx surface the caller-ID attestation level (A/B/C) for inbound calls — a "C" or unattested call is a much stronger spam/spoofing signal than nothing, and is checked before the call is fully handed to the expensive part of the pipeline (the AI can shorten its engagement — e.g. a faster silence-timeout — on low-attestation calls without outright refusing them, since false positives on a real emergency caller are unacceptable per the fail-safe principle in [07](07-notification-and-emergency.md) §5.2).
- **Per-ANI rate limiting**: the same calling number placing an abnormal volume of calls in a short window (a known robocall/scanning pattern, not a legitimate customer behavior) is throttled at the carrier/gateway layer before it reaches the voice-orchestrator at all — this protects both cost and the shared infrastructure's capacity for real callers.
- **Fast, cheap disengagement for genuinely silent/dead-air calls**: the silence-recovery-then-graceful-end state transition already specified in [03-conversation-engine.md](03-conversation-engine.md) §2/§6 (2 recovery attempts, then end) is also, incidentally, the cost control for this category — a robocall/dead-air call is not kept on an expensive STT/LLM/TTS pipeline indefinitely.

## 6. Why this belongs in the blueprint now, not as a Phase 3 afterthought

Retrofitting destination allowlisting, carrier geographic permissions, and IRSF spend caps onto a call-transfer feature that already exists in production is a much higher-risk change (touching a live, safety-critical code path) than designing it in from the first implementation of `escalateEmergency`'s transfer action ([04-ai-tool-architecture.md](04-ai-tool-architecture.md) §3.8) — this is exactly the kind of "identify features/edge cases not explicitly requested" gap a principal-level review is expected to catch before Phase 1 implementation begins, not after an incident.
